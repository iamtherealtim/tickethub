# Localization

TicketHub uses CodeIgniter's built-in language layer. Strings live in
`app/Language/<locale>/<File>.php` and views read them with `lang('File.key')`.
English (`en`) is the source of truth and the fallback; French (`fr`) is a
complete second locale that proves the mechanism.

## Files

| File            | Holds                                                                 |
|-----------------|-----------------------------------------------------------------------|
| `Common.php`    | Buttons, generic labels, theme/language names, and the display names of the fixed vocabularies (`status`, `priority`, `type`, `changeState`, `problemStatus`, `assetStatus`, `role`, `level`) |
| `Nav.php`       | Sidebar, headers, footers, account menu, command palette             |
| `Dashboard.php` | Agent dashboard                                                       |
| `Portal.php`    | Employee portal (home, knowledge base, catalog, my tickets, search)  |
| `Auth.php`      | Sign-in, password reset, first-password, sign-out, two-factor         |
| `Errors.php`    | The framework error pages (`app/Views/errors/html`)                   |
| `Validation.php`| Overrides for framework validation messages                           |

Keys are nested arrays, addressed with dots: `lang('Portal.kb.emptyTitle')`.

## How a locale is chosen

`app/Filters/Locale.php` runs before every request and picks, in order:

1. `?lang=fr` on the URL — saved to the session as `locale`, then the parameter
   is stripped with a redirect so it does not stick to pagination links.
2. The session's `locale`.
3. The `app_locale` key in Settings (the site default, set on Admin → General).
4. `Accept-Language` negotiation, because `Config\App::$negotiateLocale` is
   `true` and `$supportedLocales` is `['en', 'fr']`.

The switcher links (`EN` / `FR`) in the portal footer and in the account menu
are built by `th_lang_switcher()` and simply append `?lang=xx` to the current
URL.

## Conventions for views

- Load the helper once at the top of any view that needs it: `helper('i18n')`.
- Plain strings: `<?= lang('Portal.kb.title') ?>`. Escape when the value is
  interpolated with user data: `<?= esc(lang('Portal.home.headline', ['name' => $first])) ?>`.
- Attributes: `placeholder="<?= esc(lang('Nav.palette.placeholder'), 'attr') ?>"`.
- Parameters use ICU MessageFormat. Named (`{name}`) and positional (`{0}`)
  both work. Plurals:
  `'{0, plural, one {# response} other {# responses}}'`.
  Because the string goes through `MessageFormatter` only when arguments are
  passed, a bare apostrophe in an argument-taking string must be written as
  the typographic `’` (ICU treats `'` as a quote character).
- Stored vocabulary values (a ticket's `status`, `priority`, a user's `role`)
  are translated by key with a fallback to the raw value, so an unexpected
  value never leaks a key:

  ```php
  th_t('Common.status.' . $t['status'], $t['status'])
  th_t('Common.priority.' . $t['priority'], $t['priority'])
  ```

  `th_t()` returns the fallback whenever `lang()` returns the key unchanged.
- Helpers that render text (`th_kpi`, `th_card_head`, `th_btn`, `th_empty`,
  ...) take already-translated strings; pass `lang(...)` results in. Some
  helpers escape their arguments themselves (`th_empty`); others do not
  (`th_card_head`, `th_kpi`, `th_btn`) — wrap those in `esc()` at the call site.
- Never build a sentence from fragments (`'the ' . $name . ' queue'`). Put the
  whole sentence in the language file with a placeholder; word order differs
  between languages.
- JavaScript strings that need translating go into `window.TH.i18n` in the
  layout (see `TH.i18n.theme`) rather than into `app.js`.

### Views still to convert

The extraction so far covers the layouts, the dashboard, the portal, the auth
pages and the error pages. The agent ticket, problem, change, asset, report,
knowledge-base and admin views still carry English literals. Convert them
file by file with the same pattern: add a language file named after the area
(`Tickets.php`, `Admin.php`, ...), create the `fr` twin at the same time, and
run `tests/unit/LanguageTest.php`, which fails when the two locales drift.

## Adding a language

1. Copy `app/Language/en/` to `app/Language/<code>/` (use the ISO 639-1 code,
   e.g. `de`, `es`, `pt-BR`) and translate every value. Keep every key.
2. Add the code to `$supportedLocales` in `app/Config/App.php`.
3. Add the language's own name to `Common.php` → `lang.<code>` in **every**
   locale (`'de' => 'Deutsch'`), so the switcher can label it.
4. Run `php vendor/bin/phpunit --no-coverage tests/unit/LanguageTest.php`. The
   test checks that every locale directory has the same files and the same
   keys as `en`, and that no `en` value is empty.
5. Optionally translate the framework's own strings by copying the files you
   need from `system/Language/en/` into `app/Language/<code>/` (validation
   messages are the usual candidates).

A missing key in a secondary locale falls back to English at runtime, so a
partially translated locale still renders — the test is what keeps it honest.
